# TopicScope 研究工作台设计方案

- 日期：2026-11-06
- 项目：TopicScope · 选题雷达
- 目标：面向真实科研用户，形成“文献检索 → 方向判断 → 证据对话 → 可执行方案 → 研究档案”的完整闭环
- 适用赛事：2026 Qoder 高校创造力大赛 · StudyHack 学习科研赛道
- 状态：设计稿，待实现

## 1. 产品定位

TopicScope 不是一个只返回论文列表的搜索框，也不是一个只给出泛泛建议的聊天机器人。

它是一套证据优先的科研选题工作台：用户从一个模糊的研究兴趣出发，检索相关文献，观察方向分布和变化趋势，定位代表论文，追问已有证据，最后得到一份包含问题、方法、实验、风险和时间安排的可执行研究方案。

产品的核心承诺是三点：

1. **找得到**：能从多个来源找到相关论文，并保留检索条件、来源和时间。
2. **看得懂**：能解释某个方向为什么被判为成熟、增长中或当前覆盖不足，所有判断都能回查到数字和论文。
3. **做得成**：能把方向判断转成数据、基线、指标、实验矩阵、风险和里程碑，而不是停留在“可以进一步研究”。

## 2. 用户与主要场景

### 2.1 目标用户

- 需要快速确定论文选题的本科生、硕士生和博士生
- 正在写综述、开题或研究计划的科研人员
- 需要比较不同论文指标口径的实验人员
- 希望把一次文献阅读过程保存下来、以后继续使用的长期用户

### 2.2 典型场景

#### 场景 A：从兴趣到方向

用户输入“医学影像分割中的 Transformer”，系统返回检索范围、方向聚类、近期增长、代表论文和当前检索中的覆盖边界。用户点击一个方向，继续追问“这个方向真正解决了什么问题”。

#### 场景 B：从论文到证据

用户从文献库选择一篇论文，查看标题、摘要、方法、实验、指标和开放获取信息，并明确哪些内容只来自元数据或摘要，哪些内容已经由用户核对全文。

#### 场景 C：从证据到方案

用户要求系统基于选中的方向和论文生成研究方案。系统必须列出证据来源、假设、数据集、基线、指标、实验矩阵、算力和失败判据。

#### 场景 D：保存和复用

用户把本次检索快照、论文标注、对话结论、指标换算和研究方案导出为 Markdown/JSON，之后可以重新导入继续工作。

## 3. 产品能力命名

所有能力使用 TopicScope 自己的命名，不直接暴露外部工具或技能名称。

| 能力 | 职责 | 主要输出 |
|---|---|---|
| **TopicScope 检索台** | 多源检索、查询管理、去重和来源记录 | 结构化论文集合、检索快照 |
| **TopicScope 方向雷达** | 聚类、趋势、覆盖边界和方向诊断 | 方向卡、趋势数据、关键词网络 |
| **TopicScope 证据卡** | 单篇论文的结构化阅读和证据边界标记 | 论文卡、主张-证据关系 |
| **TopicScope 研究对话** | 基于当前语料回答问题、解释不确定性 | 可回查的回答、下一步动作 |
| **TopicScope 方案生成器** | 将方向和证据转成研究计划 | Markdown 研究方案 |
| **TopicScope 研究档案** | 保存和导出研究过程 | Markdown、JSON、版本记录 |

## 4. 用户闭环

```text
输入研究兴趣或研究问题
        ↓
TopicScope 检索台
        ↓
来源统一、去重、质量标记、检索快照
        ↓
TopicScope 方向雷达
        ↓
方向聚类、趋势、覆盖边界、代表论文
        ↓
TopicScope 证据卡
        ↓
论文方法、实验、指标、局限、证据等级
        ↓
TopicScope 研究对话
        ↓
带 evidenceIds 的回答和待核对问题
        ↓
TopicScope 方案生成器
        ↓
研究问题、假设、数据、基线、指标、实验、风险、里程碑
        ↓
TopicScope 研究档案
        ↓
可迁移的 Markdown / JSON 方案包
```

## 5. 检索台设计

### 5.1 检索输入

检索台同时接受三种输入：

1. **关键词输入**：例如 `medical image segmentation transformer`。
2. **自然语言问题**：例如“低标注医学影像分割还有哪些适合单卡复现的方向？”。
3. **约束条件**：年份、文献类型、数据集、模态、任务、方法、期刊或开放获取要求。

自然语言问题先被转换为可检查的检索表达式，并在界面显示转换结果，用户可以修改后再检索。

### 5.2 来源与降级

第一阶段支持 OpenAlex 和 Crossref，后续可增加 PubMed/Europe PMC 等医学来源。每条结果必须携带来源字段，不把不同来源混成一个没有出处的列表。

来源降级规则：

- 主来源可用：使用主题、关键词、摘要和引用数据。
- 主来源限流：切换备选来源，并明确标记“主题标签缺失”或“摘要覆盖较低”。
- 所有来源失败：保留最近一次有效快照，显示快照日期和查询条件。

### 5.3 去重与规范化

按以下顺序建立 `dedupKey`：

1. 规范化 DOI
2. OpenAlex ID 或其他来源唯一 ID
3. 标题归一化后的相似匹配

DOI 必须统一成裸 DOI 或统一 URL 形式，展示和导出使用同一种格式，避免重复拼接 DOI 域名。

### 5.4 检索快照

每次检索都保存：

- 查询原文
- 解析后的检索表达式
- 来源列表
- 年份和类型过滤器
- 请求时间
- 返回数量
- 去重数量
- 摘要覆盖率
- 开放获取覆盖率
- 是否使用缓存
- 是否发生来源降级

方向雷达中的“论文占比”必须写成“当前检索样本占比”。如果数据采用按年均衡抽样，页面必须明确说明这种抽样不能直接代表真实领域产出比例。

## 6. 方向雷达设计

### 6.1 分析对象

文档内容由标题、关键词、主题、摘要组成，并记录每个字段的权重。摘要缺失的论文仍可参与分析，但要降低其证据等级，并在结果中显示覆盖率。

### 6.2 方向指标

每个方向至少包含：

- 样本数量和样本占比
- 年份范围和中位年份
- 近三年、近五年论文比例
- 引用中位数和引用分布
- 主要期刊/会议及集中度
- 主题词和方法词
- 代表论文
- 方向内部高提升度词对
- 摘要和开放获取覆盖率
- 聚类稳定性

### 6.3 覆盖判定

不再使用容易被误解的绝对结论“真空白”。建议使用以下表达：

| 标签 | 含义 |
|---|---|
| **高密度成熟方向** | 当前检索样本中论文多、历史积累明显，常规增量竞争激烈 |
| **稳定产出方向** | 有持续研究，但仍可能通过数据、任务设定或评测设计形成差异 |
| **增长窗口** | 当前样本量不大，但近年增长明显，值得进一步核查 |
| **当前检索未观察到** | 当前检索范围内命中很少，不能直接等价于真实领域空白 |
| **证据不足** | 摘要、主题或来源覆盖不够，暂不适合做强判断 |

每个判定同时显示“判定依据”和“不能推出什么”。例如：

> 该方向在当前检索样本中近三年占比高，表现为增长窗口；这不能证明该方向尚未被其他数据库或未公开论文覆盖。

### 6.4 聚类可信度

聚类数不应只由语料规模决定。后续版本应支持：

- 多个候选 k 的轮廓系数比较
- 不同随机种子的稳定性
- 空簇和极小簇提示
- 用户手动合并/拆分方向
- 长尾簇的“可能偏题”提示

方向卡应提供“算法结果”和“用户判断”两层，避免把无监督聚类当成领域共识。

## 7. 证据卡设计

### 7.1 证据等级

每篇论文必须明确当前材料范围：

| 等级 | 可支持的内容 |
|---|---|
| `metadata` | 标题、作者、年份、期刊、引用数、 DOI |
| `abstract` | 摘要中明确写出的任务、方法和结果 |
| `full_text` | 正文、图表、公式和实验细节 |
| `user_verified` | 用户明确标记已人工核对的内容 |

系统不能把摘要推断写成正文事实，也不能在没有全文时补写表格数字。

### 7.2 证据卡字段

每张证据卡包含：

- 文献元数据
- 研究问题
- 核心贡献
- 方法流程
- 数据集与划分
- 基线
- 指标和统计方式
- 主要结果
- 消融或敏感性分析
- 作者声明的局限
- 当前材料无法判断的内容
- 可复现入口：代码、数据、开放获取链接
- 可迁移的研究问题

### 7.3 主张-证据关系

每条重要结论都要绑定一个或多个 `EvidenceRef`。证据引用使用稳定 ID，不使用模型自由输入的模糊文本。

```ts
type EvidenceRef = {
  id: string;
  paperId: string;
  sourceLevel: "metadata" | "abstract" | "full_text" | "user_verified";
  locator?: string;
  claim: string;
  value?: string | number;
};
```

## 8. 研究对话设计

### 8.1 对话范围

研究对话只允许使用：

- 当前检索快照
- 当前选中的论文
- 当前方向雷达的统计结果
- 用户主动输入的事实
- 已保存的证据卡

系统可以提出下一步检索建议，但不能把没有查到的论文、数字、作者或结论伪装成已知事实。

### 8.2 回答结构

每次回答包含：

1. 结论
2. 证据依据
3. 不确定性
4. 不能由当前材料推出的内容
5. 推荐的下一步动作

示例：

```json
{
  "answer": "当前语料显示该方向在近三年增长明显，但还不能证明其真实研究密度较低。",
  "evidenceIds": [
    "cluster:mamba-state-space:recentShare",
    "snapshot:2026-11-06:sampleFrame"
  ],
  "uncertainty": "metadata_and_abstract_only",
  "nextAction": "扩大检索式并核查代表论文的实验部分"
}
```

### 8.3 研究对话的安全边界

- 模型 API key 只能放在服务端 Secret，不能写入源码。
- 公开接口需要限流和调用额度保护。
- 对话结果不自动写入正式方案，用户确认后才进入档案。
- 每次方案生成保存模型、时间、输入快照和证据 ID。
- 如果证据不足，系统必须返回“无法从当前材料判断”。

## 9. 方案生成器设计

### 9.1 方案结构

生成器输出固定 Markdown 结构：

```markdown
# 研究方案：{题目}

## 1. 一句话研究问题
## 2. 背景与已有证据
## 3. 方向位置与新颖性边界
## 4. 可验证假设
## 5. 数据集与获取方式
## 6. 基线与对照
## 7. 方法设计
## 8. 指标与统计方法
## 9. 实验矩阵
## 10. 复现与资源需求
## 11. 风险与失败判据
## 12. 里程碑与时间安排
## 13. 预期结果与替代路线
## 14. 参考文献
## 15. 证据索引
```

### 9.2 方案质量要求

每份方案必须回答：

- 为什么现在值得做
- 与已有论文的差异在哪里
- 最小可行实验是什么
- 如果主假设失败，如何判断失败
- 哪些数据、代码或算力仍未具备
- 哪些结论是证据，哪些只是待验证假设

“创新点”不能只写“结合 A 和 B”。必须说明任务差异、数据差异、评测差异或机制假设差异。

### 9.3 方案评分

方案生成器给出五项可解释评分，每项 1–5 分：

- 证据充分度
- 研究问题清晰度
- 基线可获得性
- 资源可行性
- 风险可控性

总分只用于排序，不替代用户判断。评分旁边必须显示扣分原因和需要补充的材料。

## 10. 研究档案与数据结构

### 10.1 核心对象

```ts
type PaperProvenance = {
  source: "openalex" | "crossref" | "pubmed" | "user_import";
  sourceId: string;
  retrievedAt: string;
  query?: string;
  filter?: string;
  dedupKey: string;
  abstractAvailable: boolean;
  fullTextAvailable: boolean;
  oaUrl?: string | null;
};

type ResearchSession = {
  id: string;
  createdAt: string;
  updatedAt: string;
  query: string;
  snapshot: SnapshotMeta;
  selectedPaperIds: string[];
  evidence: EvidenceRef[];
  conversations: ConversationTurn[];
  metricChecks: MetricCheck[];
  plan?: ResearchPlan;
};
```

### 10.2 本地优先

第一阶段使用浏览器 IndexedDB 保存研究会话，支持：

- 新建、复制、重命名和删除会话
- 导出 Markdown
- 导出 JSON
- 从 JSON 恢复会话
- 记录方案版本

不要求用户登录，不默认上传论文内容。后续如增加云端同步，必须明确同步范围和删除方式。

## 11. 当前项目的改造边界

### 11.1 保留部分

- 现有 React + TypeScript + Vite 架构
- 现有 OpenAlex/Crossref 适配器
- 现有 TF-IDF、聚类、共现和指标换算模块
- 现有离线快照机制
- 现有 Markdown/CSV 导出能力

### 11.2 优先调整部分

1. 将论文来源和检索条件从临时状态提升为正式 provenance 数据。
2. 将方向判定中的“真空白”改成有边界的检索结论。
3. 增加 DOI 规范化和跨源去重。
4. 为聚类结果增加稳定性和样本偏差提示。
5. 为研究对话引入稳定 `evidenceIds`。
6. 将方案生成和档案保存设计成独立模块。
7. 移除源码中的硬编码模型密钥，增加公开接口限流。
8. 为 Canvas 图增加列表/表格替代视图和键盘访问。

### 11.3 暂不纳入首版

- 用户账户体系
- 多人实时协作
- 自动全文下载和大规模 PDF 解析
- 复杂知识图谱
- 自动判断论文“是否有创新”
- 自动替用户投稿或发送外部消息

这些功能会显著扩大隐私、版权、存储和验证范围，不适合作为第一阶段的核心承诺。

## 12. 分阶段实现路线

### Phase 0：信任基础

- 删除硬编码 API key，改用环境 Secret
- 修复 DOI 链接规范化
- 移除未使用的高风险依赖
- 建立基础测试命令和 CI
- 初始化 Git 和版本记录

### Phase 1：检索台与 provenance

- 增加 `PaperProvenance`
- 保存检索快照
- DOI/标题/来源 ID 去重
- 显示摘要覆盖、开放获取覆盖和来源降级
- 完善导出字段

### Phase 2：方向雷达可信度

- 增加样本框说明
- 改写覆盖判定标签
- 增加聚类稳定性
- 增加用户合并/拆分方向
- 优化短语和领域噪声处理

### Phase 3：证据卡与研究对话

- 增加论文详情页
- 增加证据等级和人工核对标记
- 让模型回答绑定 `evidenceIds`
- 保存对话摘要和下一步动作

### Phase 4：方案生成与研究档案

- 固定 Markdown 方案模板
- 生成证据索引和风险清单
- IndexedDB 会话存储
- Markdown/JSON 导入导出
- 方案版本比较

### Phase 5：持续更新

- 定时检索新论文
- 方向变化提醒
- 研究周报
- 可选通知和团队协作

## 13. 验收指标

### 产品指标

- 新用户从输入问题到生成第一份方案不超过 10 分钟
- 任何方向判断都能在 2 次点击内查看依据
- 每份方案都包含数据、基线、指标、风险和里程碑
- 方案可导出为结构完整的 Markdown
- 关闭网络后，已保存会话仍能查看和导出

### 可信度指标

- 论文去重结果可解释
- 每条模型结论至少绑定一个证据 ID，或明确标记“无证据支持”
- 证据等级不会被模型自动升级
- “当前检索未观察到”不会被展示为绝对研究空白
- 快照包含查询、来源、时间和过滤条件

### 工程指标

- 现有 540 篇离线快照分析继续保持浏览器内秒级完成
- 主要计算逻辑有确定性测试
- 在线检索失败时仍可加载最近快照
- 公开模型接口具备限流和失败降级
- 导出文件不包含 API key 或隐藏凭据

## 14. 竞赛展示路径

建议用一个“从问题到方案”的完整案例，不把展示重点放在功能数量上：

1. 输入“低标注医学影像分割中的长程建模”。
2. 展示检索范围、来源和摘要覆盖率。
3. 展示雷达发现的增长窗口与样本边界。
4. 选中两篇代表论文，打开证据卡。
5. 询问“哪些结论仍然缺少全文证据”。
6. 调整约束：单卡、公开数据、三个月完成。
7. 生成完整 Markdown 研究方案。
8. 展示方案中的证据索引、最小可行实验和失败判据。
9. 导出方案和研究档案。

这个演示能同时证明：TopicScope 找得到论文、解释得清方向、知道证据边界，并且能帮助用户开始真正的研究。

## 15. 最终定位文案

> TopicScope 是一个证据优先的科研选题工作台。它从文献检索开始，帮助用户看清研究方向的分布、趋势和覆盖边界，围绕代表论文建立可核对的证据链，再通过受约束的研究对话生成一份包含问题、方法、实验、风险和时间表的可执行方案。

## 16. 方法提炼与 TopicScope 适配实施

本节把成熟科研工作流中的可迁移方法转化为 TopicScope 自己的实现规则。实现时只采用方法思想和数据契约，不直接暴露外部工具名称，也不把外部流程原样搬进前端。

### 16.1 TopicScope 检索路由

#### 目标

把“一次搜索”变成可解释的检索任务：先规划来源和查询式，再执行检索，最后报告覆盖边界。

#### 实施步骤

1. 从用户问题中提取四类概念：研究对象、任务、方法、约束。
2. 生成三组查询式：
   - 核心词组：保持用户原意，用于高精度检索；
   - 同义扩展：补充缩写、同义词和常见术语；
   - 约束扩展：加入数据集、模态、年份或方法限定。
3. 按来源能力分配查询：
   - OpenAlex：主题、摘要、引用和作者机构；
   - Crossref：DOI、期刊、作者和基础书目；
   - 后续医学来源：疾病、模态、临床任务和医学主题词；
   - 本地快照：断网或接口失败时提供稳定基线。
4. 为每条来源记录返回数量、失败原因、摘要覆盖率和去重数量。
5. 如果主来源失败，执行降级路径，但禁止把降级结果伪装成同等质量的数据。

#### 数据契约

```ts
type SearchJob = {
  rawQuestion: string;
  queryVariants: string[];
  constraints: {
    fromYear?: number;
    toYear?: number;
    types?: string[];
    openAccessOnly?: boolean;
  };
  sourcePlan: Array<"openalex" | "crossref" | "pubmed" | "snapshot">;
};

type SearchReport = {
  job: SearchJob;
  sourceReports: SourceReport[];
  totalBeforeDedup: number;
  totalAfterDedup: number;
  abstractCoverage: number;
  fullTextCoverage: number;
  limitations: string[];
};
```

#### 与现有项目的对应

- `lib/data/retrieval.ts`：负责缓存、主来源和降级流程；
- `lib/data/openalex.ts`、`lib/data/crossref.ts`：负责来源适配；
- `lib/data/types.ts`：增加来源、检索时间和去重字段；
- `hooks/useCorpus.ts`：将 `SearchReport` 传递到雷达和导出层。

### 16.2 TopicScope 研究评分

#### 目标

用统一的评分帮助用户从几十篇候选论文中挑出值得先读的论文，但评分只用于排序和解释，不能替代科学判断，也不把期刊名简单等同于论文质量。

#### 六个维度

| 维度 | 权重 | 计算依据 |
|---|---:|---|
| 问题匹配度 | 30 | 查询词、任务、对象和用户约束的匹配 |
| 方法相关度 | 20 | 方法词与目标方向的相似度、方向簇归属 |
| 证据完整度 | 15 | 摘要、全文、图表和实验信息的可获得程度 |
| 可复现程度 | 15 | 代码、数据集、配置和开放获取入口 |
| 时效与趋势价值 | 10 | 发表年份、近年增长和方向变化 |
| 用户约束适配 | 10 | 算力、时间、数据许可和任务条件 |

每项分数都保存理由。例如：

```ts
type ScoreBreakdown = {
  dimension: string;
  score: number;
  max: number;
  reason: string;
  evidenceIds: string[];
};
```

#### 实施规则

- 缺少摘要不能自动判为低质量，只能降低证据完整度；
- 没有代码不能直接判定不可复现，应标记为“需要自行重建”；
- 引用数只作为背景信号，不直接增加方法优越性分数；
- 评分结果必须能拆回六个维度，禁止只显示一个无法解释的总分；
- 评分应支持用户按“低算力”“最新”“开放数据”等偏好重新排序。

### 16.3 TopicScope 证据阅读卡

#### 目标

把“读过论文”拆成可检查的字段，区分原文事实、摘要事实、用户判断和模型推断。

#### 阅读流程

1. 先登记元数据和访问状态；
2. 再提取研究问题、数据、方法、基线、指标和结果；
3. 逐条建立“主张 → 证据位置”的关系；
4. 记录作者声明的局限和当前材料无法判断的部分；
5. 最后才生成研究启发，且启发必须标记为假设而不是事实。

#### 当前项目的分阶段适配

- 当前版本只有元数据和摘要：只能生成 `metadata` 或 `abstract` 级证据卡；
- 用户打开开放获取链接并手动核对后，可以把字段标记为 `user_verified`；
- 后续加入 PDF 解析时，保存 PDF 页码、章节、图表和公式定位；
- 解析失败时保留结构化文本证据，不编造页码或图表编号。

#### 证据卡最小字段

```ts
type PaperCard = {
  paperId: string;
  sourceLevel: "metadata" | "abstract" | "full_text" | "user_verified";
  researchQuestion: Claim;
  contribution: Claim[];
  data: Claim[];
  method: Claim[];
  baselines: Claim[];
  metrics: Claim[];
  results: Claim[];
  limitations: Claim[];
  notAssessable: string[];
  nextQuestions: string[];
};

type Claim = {
  text: string;
  evidenceIds: string[];
  status: "source_fact" | "user_judgment" | "model_hypothesis";
};
```

### 16.4 TopicScope 方向缺口分析

#### 目标

从“论文少”升级为多信号诊断，避免把检索召回不足误判成研究空白。

#### 缺口候选的四个信号

1. **密度信号**：方向或词对在当前样本中出现较少；
2. **趋势信号**：近年增长明显，或刚出现新的方法组合；
3. **组合信号**：两个已有方向之间的组合较少；
4. **证据信号**：已有工作中实验、数据或评测仍不完整。

只有至少两个信号同时成立，才生成“值得进一步核查的候选方向”。输出必须包含：

- 支持该候选的数字；
- 可能的检索偏差；
- 需要补查的关键词和来源；
- 不能推出的强结论。

#### 推荐输出格式

```text
候选方向：低标注 + 长程建模
支持信号：近三年占比、组合提升度、公开基线数量
当前证据：摘要级，未完成全文核查
检索风险：样本按年份均衡，不能代表真实论文总量
下一步：补充同义词、数据集名称和医学主题词后重新检索
```

#### 与现有雷达的适配

- `lib/analysis/radar.ts`：保留聚类和年份统计，新增 `coverageConfidence`、`sampleFrame` 和 `gapSignals`；
- `lib/analysis/cooccurrence.ts`：将词对提升度作为组合信号之一，而不是单独证明研究空白；
- `components/RadarView.tsx`：显示“支持信号”和“不能推出的结论”；
- `components/DirectionAdvisor.tsx`：只接收结构化信号，不把整批原始摘要直接发送给模型。

### 16.5 TopicScope 受约束研究对话

#### 上下文组装

每次对话先生成一个有限上下文包：

```ts
type ResearchContextPack = {
  question: string;
  searchReport: SearchReport;
  selectedClusters: ClusterBrief[];
  selectedPapers: PaperCard[];
  evidence: EvidenceRef[];
  userConstraints: {
    time?: string;
    compute?: string;
    dataAccess?: string;
    targetOutput?: string;
  };
};
```

模型只能从上下文包推理。回答格式固定为：

```json
{
  "answer": "...",
  "evidenceIds": ["..."],
  "uncertainty": "...",
  "notSupported": ["..."],
  "nextAction": "..."
}
```

#### 交互模式

- **解释模式**：解释方向、论文方法和指标；
- **比较模式**：比较选中的论文，但要求统一任务和指标口径；
- **质疑模式**：主动寻找证据不足、样本偏差和不可比之处；
- **规划模式**：在用户给出时间、算力和数据约束后生成方案；
- **复盘模式**：根据实验日志更新风险和下一步。

### 16.6 TopicScope 方案生成实施

#### 生成前的约束收集

方案生成前必须收集或确认：

- 研究对象和任务
- 可用数据集或数据获取渠道
- 目标完成时间
- GPU/CPU/存储条件
- 是否要求开放代码
- 可接受的实验规模
- 预期论文、开题或内部技术报告格式

缺少关键约束时，方案生成器输出“待补充条件”，不能自行猜测。

#### 三层实验设计

每份方案都拆成三层：

1. **最小可行实验**：一套数据、一个主基线、一个核心指标，验证假设是否值得继续；
2. **主实验**：加入多个基线、消融、不同随机种子和统计区间；
3. **扩展实验**：跨数据集、跨模态、效率分析或临床/实际场景验证。

每层都要写出时间、算力、成功标准和失败后的替代路线。

#### 方案质量门槛

生成结果必须通过以下检查：

- 研究问题能被一句话回答；
- 至少有一个可证伪假设；
- 每个主要主张有证据 ID 或标为待验证；
- 至少列出一个可获得的基线；
- 指标和数据划分与任务一致；
- 有明确失败判据；
- 没有把“组合 A+B”直接写成创新性结论。

### 16.7 TopicScope 研究日志

#### 记录内容

一次研究会话至少记录：

- 研究问题和查询式
- 来源、过滤器和检索时间
- 数据快照版本
- 用户选中的方向和论文
- 用户标注的证据和疑问
- 指标换算记录
- 对话摘要和模型版本
- 方案版本、修改时间和用户确认点
- 实验执行结果、异常和下一步

#### Markdown 日志模板

```markdown
---
session_id: TS-20261106-001
question: 低标注医学影像分割中的长程建模
snapshot: snapshot-medical-segmentation@2026-11-06
evidence_level: abstract
status: planning
---

# 研究会话

## 当前判断
## 已核对证据
## 尚未解决的问题
## 方案版本
## 下一步动作
## 风险与异常
```

### 16.10 TopicScope 数据与代码可用性核验

研究方案不能只列出数据集名称，还要说明用户能否真正取得和使用它。对每个数据集、代码库和预训练模型，记录以下状态：

| 状态 | 含义 |
|---|---|
| `public` | 有公开链接，许可和访问入口清楚 |
| `controlled` | 需要申请、注册或伦理审批 |
| `third_party_restricted` | 受第三方许可或商业条件限制 |
| `within_paper` | 论文中描述，但没有独立下载入口 |
| `not_verified` | 当前材料没有足够信息判断 |

方案生成器必须把“数据可获得”与“方法可复现”分开判断：

- 数据公开不代表标注、预处理和划分公开；
- 代码公开不代表依赖、权重和训练配置完整；
- 论文给出结果不代表可以在当前算力下复现；
- “可联系作者获取”只能作为弱可用性，不应显示为公开可用。

推荐的数据结构：

```ts
type ResourceRoute = {
  kind: "dataset" | "code" | "model" | "annotation";
  name: string;
  status: "public" | "controlled" | "third_party_restricted" | "within_paper" | "not_verified";
  url?: string;
  license?: string;
  accessCondition?: string;
  verifiedAt?: string;
  evidenceIds: string[];
};
```

### 16.11 TopicScope 持续更新管线

长期使用时，检索台可以扩展成一个低频更新管线，但更新管线必须与前端交互解耦：

```text
定时触发
  → 按保存的 SearchJob 检索
  → DOI / 标题 / 来源 ID 去重
  → 计算六维分数
  → 与上一次快照比较
  → 标记新增方向、方向增长和证据变化
  → 生成 Markdown 周报
```

每次更新至少产生三类变化：

- 新增论文：为什么进入当前方向；
- 方向变化：样本量、趋势或组合信号如何改变；
- 证据变化：新增全文、代码、数据或引用信息。

前端首版只需要支持“手动刷新”和“比较两个快照”。定时任务、通知和团队共享放在后续版本，避免把部署复杂度提前引入核心产品。
